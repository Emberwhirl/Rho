# Rho 0.3.x Scientific Workflow Implementation Handoff

Status: active implementation contract

Date: 2026-07-25  
Baseline: `07c338e` (`0.2.0-dev.12`, clean `main` at handoff time)  
Target milestone: `0.3.x` scientific workflow foundation

## How To Use This Brief

This document is the implementation and review contract for `0.3.x`. It is not
permission to redesign Rho or to implement the whole roadmap in one change.
The implementation agent must complete and hand back one work package at a
time. A separate review agent will inspect the diff, rerun the relevant gates,
and decide whether the next package may start.

Start with **WP1 only**. Do not begin WP2-WP4 until WP1 has been reviewed and
accepted. If the baseline has moved from `07c338e`, report the new commit and
reconcile this document against the intervening changes before editing code.

Before implementation, read:

- `docs/project/active-development-roadmap.md`;
- `docs/implementation/implemented-windows-build-environment.md`;
- `docs/plans/implemented-0.2x-agent-handoff.md`;
- `docs/design/implemented-agent-file-editing-design.md`;
- `docs/design/implemented-agent-llm-configuration-design.md`.

## Release Boundary

`0.3.x` feature development may proceed while `0.2.0` manual release
acceptance remains open. These are separate facts:

- the current code is an internal Windows candidate, not a confirmed public
  `0.2.0` release;
- clean-install, complete QC-workflow, SmartScreen/distribution and uninstall
  evidence remain governed by the active `0.2.0` release documents;
- passing `0.3.x` automated tests must not be reported as satisfying those
  manual `0.2.0` gates;
- no implementation package in this brief authorizes publishing a release,
  changing signing policy or installing a newly built package over a running
  Rho instance.

Do not change the product version at the start of WP1. Version and NEWS updates
belong in the first reviewed integration change after WP1 behavior is accepted.

## Architecture Invariants

Every work package must preserve:

- Workspace R as the only authority for live scientific objects and project
  execution;
- Agent R as the `aisdk` host, never as a second scientific workspace;
- Rust broker ownership of transport, workspace/project revisions, approvals,
  durable run records and process lifecycle;
- exact stale-revision checks before a scientific or filesystem mutation;
- explicit user review for package installation, lockfile changes, project
  bootstrap and other environment mutations;
- bounded, plain JSON-serializable values across R/Rust/frontend boundaries;
- project-root path validation before reads, writes, renders or exports;
- no Python, Jupyter Server, JupyterLab, Electron, unrestricted shell or second
  production frontend;
- no changes to `aisdk`, `aisdk.console` or `aisdk.bioc` repositories unless a
  concrete missing boundary is demonstrated, documented and separately
  approved;
- browser-mode mock behavior sufficient to exercise each new frontend state
  without a running Tauri backend.

Never parse Console text as the authoritative result of an environment
operation. Structured R results and broker events are the contract.

## Current Baseline: Do Not Reimplement

The following foundations already exist in `0.2.0-dev.12`:

- read-only `renv` presence/activity detection;
- R version, library paths, attached-package and Bioconductor version summary;
- bounded previews for data frames, matrices, vectors and lists;
- object metadata and bounded structure inspection;
- project-scoped plot history with run/source/revision provenance;
- saved `.qmd` and `.Rmd` rendering with structured result and Problems output;
- durable executions, Agent approvals, restart recovery and project revisions;
- Agent file-edit proposals with explicit Accept/Reject handling.

`0.3.x` extends these contracts with controlled operations, richer bounded
inspection and reproducibility evidence. Replacing them with parallel state,
another database or raw R/terminal plumbing is out of scope.

## Milestone User Workflow

The milestone is complete only when a second user can take a selected QC result
and determine, without relying on chat text alone:

1. which project, source document, document revision and Workspace run produced
   it;
2. which R, Bioconductor and package environment was used;
3. whether the project environment differs from its lockfile;
4. which reviewed operation changed the environment, if any;
5. which plot, render or exported summary is the resulting artifact;
6. how to restore the recorded project environment and rerun the source.

The implementation does not need bit-for-bit reproducibility across operating
systems. It must make inputs, operations, drift and provenance explicit.

## Work Packages

### WP1: Reviewed `renv` Operations And Environment Evidence

Goal: turn the existing read-only environment summary into a safe,
project-scoped environment workflow.

Implement:

- a structured environment refresh result that distinguishes lockfile
  presence, activation, synchronization/drift, library location, R version and
  Bioconductor version;
- a bounded, read-only `renv` status/diff preview before any mutation, including
  package name, lockfile version, library version and change direction;
- typed broker operations for `initialize`, `restore` and `snapshot`; do not
  expose an arbitrary command or shell string;
- an explicit confirmation surface showing the exact project, operation,
  expected workspace/project revisions and bounded package-change preview;
- a durable run/operation record with start/end state, revisions, result,
  warnings, errors and cancellation outcome;
- environment refresh after success, partial failure or cancellation;
- clear degraded states when `renv` is unavailable, the lockfile is invalid,
  the project is read-only, required repositories are unavailable, or a
  restart is required;
- Agent access through the existing approval machinery. Ask and Plan may inspect
  or propose; only an explicitly approved Act continuation may mutate.

Operation rules:

- `status` and diff preview are read-only and bounded;
- `initialize`, `restore` and `snapshot` are mutations even when `renv` expects
  no package change;
- confirmation is single-use and bound to operation arguments plus current
  workspace/project identity;
- a stale project or workspace revision invalidates confirmation and requires
  a fresh preview;
- do not silently install `renv`, `BiocManager` or any other package;
- do not silently change CRAN/Bioconductor repositories;
- do not silently activate a different library in the running Workspace R;
- do not claim rollback after a partial package installation. Report the
  partial state and require refresh/recovery;
- lockfile and project-file changes must advance `project_revision` and flow
  through the existing watcher/coalescing behavior;
- long operations must remain cancellable, but cancellation must be reported as
  best effort because package installation may have completed partial writes.

Preferred implementation boundaries:

- environment probes and structured `renv` calls in `r/rho.bridge`;
- typed command, revision/approval enforcement and run persistence in the Rust
  broker/Tauri boundary;
- controls and result states in the existing Environment panel;
- existing run and Problems stores rather than a new environment database.

Required automated tests:

- no lockfile, valid synchronized lockfile, drifted lockfile and malformed
  lockfile fixtures;
- missing `renv` and unavailable repository/network failure results;
- preview bounds for large package sets and long diagnostic messages;
- approval is bound to exact operation, project and revisions;
- Ask/Plan mutation rejection and stale-approval rejection;
- successful snapshot advances the project revision and refreshes state;
- failure and cancellation preserve a durable truthful terminal state;
- all R results cross JSON serialization without environments, R6 objects or
  conditions leaking into the payload;
- browser mock states for absent, synchronized, drifted, running, failed and
  cancelled operations.

Manual acceptance for WP1:

1. Open a disposable R project whose path contains a space and non-ASCII text.
2. Preview environment status without changing any project file.
3. Initialize or snapshot only after reviewing the confirmation.
4. Change one package version in the disposable fixture and verify the bounded
   preview describes the drift before restore.
5. Reject one operation and verify no project or library change.
6. Make a preview stale, then verify the old confirmation cannot execute.
7. Cancel or deliberately fail one operation and verify the UI reports partial
   state honestly and can refresh afterward.
8. Restart Rho and verify the operation record remains linked to the project.

Stop after WP1 and hand it back for review.

### WP2: Paged Data And Bioinformatics Object Viewers

Goal: inspect useful scientific objects without unbounded serialization or
accidentally evaluating arbitrary object code.

Implement after WP1 acceptance:

- server-side page requests for data frames and matrix-like objects with fixed
  maximum rows, columns, cell bytes and total response bytes;
- stable page metadata: object name, classes, dimensions, state revision,
  requested window and truncation flags;
- explicit stale-object handling when Workspace R changes between pages;
- bounded adapters for a small approved first set of common Bioconductor
  containers selected from repository/test fixtures, not a generic S4 dump;
- an unframed, keyboard-navigable viewer surface using the existing Analyze /
  Environment workflow;
- export of the currently visible bounded table to a project-scoped file only
  after explicit path review and without presenting it as a full-object export.

Before coding a Bioconductor adapter, add a short design section naming the
supported classes, package/version fixtures and fields exposed. Optional
packages must remain optional at startup.

Do not implement arbitrary R expression evaluation, full object download,
browser-side sorting of unbounded data, hidden package installation or HTML
widget execution in this package.

Required evidence:

- boundary tests at zero, exact limit and over-limit dimensions;
- long strings, list columns, missing values, Unicode and duplicate column
  names;
- stale revision between page requests;
- absent optional Bioconductor packages and unsupported S4 classes;
- visual screenshots at desktop and narrow-window sizes with no overlap;
- a payload-size assertion for every viewer response class.

### WP3: Artifact Export And Provenance Inspection

Goal: make plots, renders and visible-table exports reviewable project
artifacts linked to their generating evidence.

Implement after WP2 acceptance:

- explicit plot export using supported existing display payloads and reviewed
  project-relative destinations;
- durable render and table-export artifact records using the existing broker
  store and project isolation rules;
- an artifact detail view linking project, run, source path, document version,
  workspace identity/revisions, creation time and output path;
- a visible `incomplete provenance` state when source or document revision is
  unavailable; never infer completeness from a filename;
- missing/moved artifact recovery that preserves the record and reports the
  file as unavailable;
- bounded history loading and retention behavior.

Do not build a general file manager, overwrite an existing artifact without a
separate confirmation, execute generated HTML with privileged Tauri access or
claim content-addressed reproducibility without hashing the relevant inputs.

Required evidence:

- project isolation and path traversal tests;
- collision, missing file, stale source, incomplete provenance and restart
  recovery tests;
- plot/render/table artifacts link to the correct run rather than merely the
  latest run;
- exported bytes and displayed extension agree for each supported format;
- visual tests for long paths, empty history and missing artifacts.

### WP4: Project Skills And First Semantic Adapter

Goal: add a narrow, auditable project-specific scientific guidance layer after
the local environment, object and artifact contracts are stable.

This package requires a reviewed design checkpoint before implementation. The
design must define:

- the project-local skill directory, manifest schema, discovery bounds and
  trust status;
- whether skill files are instructions, data references or executable code;
- how edits are proposed and accepted without bypassing the existing Agent
  file proposal flow;
- prompt-injection and secret-disclosure boundaries for project-controlled
  content;
- the exact first `aisdk.bioc` use case, input/output schema, optional package
  requirements and Workspace R probe;
- compatibility behavior when `aisdk.bioc` is absent or has an unsupported
  version.

The first semantic adapter must solve one concrete QC interpretation task and
return bounded structured evidence. It must not introduce a general MCP host,
autonomous package installation, arbitrary project code execution, an upstream
`aisdk` family refactor or claims broader than its fixtures demonstrate.

Required evidence:

- invalid/oversized manifest and symlink/out-of-root discovery tests;
- untrusted skill content is clearly identified and cannot mutate in Ask or
  Plan mode;
- adapter results remain JSON-serializable and tied to workspace revisions;
- absent dependency, unsupported object and oversized-result behavior;
- one opt-in real workflow with the exact package/model versions recorded.

## Cross-Package Validation

Run the narrow tests while iterating, then run the repository baseline before
each handoff:

```powershell
node --check desktop\dist\app.js
Rscript -e "testthat::test_local('r/rho.bridge')"
Rscript -e "testthat::test_local('r/rho.agent')"
cargo test --workspace
```

Also run formatting and release metadata checks appropriate to the changed
files. Use the GNU/Rtools environment documented in
`implemented-windows-build-environment.md` before claiming Windows release
build compatibility. A debug/MSVC test run alone is not packaging evidence.

For UI changes, start the browser preview and record screenshots for at least:

- 1440 x 900 desktop;
- 1024 x 768 constrained desktop;
- a narrow window at or below 720 CSS pixels.

Check the browser console, text containment, panel resizing, keyboard focus and
mock/backend parity. Screenshots are review evidence, not a substitute for
behavioral tests.

Real package restore, Bioconductor and model/network tests must be opt-in and
must use a disposable project/library. Unit and default integration tests must
not mutate the developer's active R library or require credentials/network.

## Required Handoff Report

For every work package, report:

- baseline commit and final commit or complete working-tree diff;
- changed files grouped by R, Rust, frontend, tests and documentation;
- `git status --short` summary, including pre-existing changes;
- commands run with exact pass/fail/skip counts;
- Rust, R, Node, Ark, `renv`, Bioconductor and relevant package versions;
- manual workflow steps and screenshots for UI changes;
- which operations used a disposable project/library;
- skipped checks and the reason for each skip;
- known limitations, partial-failure behavior and follow-up work;
- explicit confirmation that no `aisdk` family repository was changed, or the
  separately approved issue/design that authorized it;
- explicit confirmation that no release was published or installed over a
  running Rho instance.

Do not describe a work package as complete when only its happy path or frontend
mock is implemented.

## Review Protocol

The review agent will lead with findings and inspect, in this order:

1. unreviewed package, project or filesystem mutation;
2. Workspace R authority and stale workspace/project revision handling;
3. data loss, partial install/restore truthfulness and dirty-file interaction;
4. approval bypass across Ask, Plan, Act and direct user controls;
5. out-of-root paths, symlinks, credential leakage and project isolation;
6. unbounded serialization, payload amplification and unsafe object evaluation;
7. run/artifact provenance correctness and restart persistence;
8. cancellation, crash and recovery behavior;
9. UI accessibility, narrow-window behavior and browser/Tauri parity;
10. missing tests, version drift and documentation overclaims.

Review outcomes are one of:

- **accept**: all package gates pass and no blocking finding remains;
- **accept with follow-up**: only explicitly documented non-blocking work
  remains;
- **changes required**: implementation returns to the same work package;
- **re-scope required**: an architecture or dependency decision exceeds this
  contract and needs user approval.

Only an accepted work package unlocks the next one.

## Explicitly Deferred Beyond 0.3.x

- macOS/Linux production packaging and cross-platform release claims;
- debugger/DAP, remote Workspace R, SSH, Slurm and containers;
- long-running jobs as a separate scheduler;
- general MCP connectors and autonomous scientific browsing;
- arbitrary HTML widget execution;
- full package-management IDE parity;
- global or cloud skill marketplaces;
- installer signing, auto-install and silent update behavior;
- broad `aisdk` family API redesign.

## Definition Of 0.3.x Done

`0.3.x` is implementation-complete only when WP1-WP4 have each been reviewed,
the milestone user workflow passes in a disposable representative project, the
repository-wide automated suite is green, and all skipped manual or external
checks are recorded. Public-release readiness remains a separate release
decision with installer and human acceptance evidence.
